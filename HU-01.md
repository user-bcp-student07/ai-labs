# HU-01: Emisión segura del token de autenticación

## Origen

- **H-AUTH-03** — `auth/src/main/java/com/bcp/workshop/auth/LegacyTokenUtil.java:8,14-15`
- **H-AUTH-07** — `auth/src/main/java/com/bcp/workshop/auth/AuthResource.java:39-49`; `docs/ENDPOINTS.md:41-51,169-174`

## Contexto

El token actual codifica contenido en Base64 y agrega un secreto constante, pero no cuenta con una firma criptográfica que permita comprobar su integridad. La sustitución debe considerar el contrato HTTP observado para `POST /auth/login`: la respuesta incluye `token`, `expiresIn`, `user` y `debug`. El formato criptográfico y la compatibilidad con consumidores no están definidos en los hallazgos y requieren coordinación; no se presupone un formato o algoritmo específico.

## Ajustes necesarios

- Sustituir la emisión actual por un token cuya integridad y autenticidad puedan verificarse mediante una firma criptográfica.
- Evitar que el token dependa de un secreto constante incluido en el código.
- Mantener la ruta y la estructura de campos observadas en la respuesta de login; acordar con los consumidores cualquier cambio incompatible al formato del token antes de adoptarlo.

## Criterios de aceptación

1. Una prueba verifica que un token recién emitido supera la comprobación de firma correspondiente.
2. Una prueba modifica el token emitido y verifica que la comprobación de firma lo rechaza.
3. Una prueba de `POST /auth/login` verifica que la respuesta exitosa conserva los campos `token` (string), `expiresIn` (entero), `user` (objeto) y `debug` (string), sin exigir un valor fijo para el token.
4. Una prueba de contrato verifica que la emisión sigue disponible en `POST /auth/login`.

## Evidencia esperada

- Salida de las pruebas automatizadas de firma: token emitido aceptado y token alterado rechazado.
- Salida de las pruebas de contrato de `POST /auth/login`, con los campos y tipos de respuesta verificados y sin publicar valores de tokens, secretos ni credenciales.
